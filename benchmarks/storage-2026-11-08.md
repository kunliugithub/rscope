# Initial storage comparison

Single sequential Linux run on generated Python input, not a kernel benchmark
or a prediction for a 40-million-line repository. Both executables were built
with `--release --locked`, Rust 1.99.1 and the same locked dependencies.
The baseline is commit `af74e35` (schema 2). The candidate is the schema 3
working tree, including the cached AST body-field lookup.

Input: 100 files, 100,000 lines, 3,997,400 bytes. Each file contains one function
and 333 repetitions of an assignment/call, a comment with `needle`, and an
augmented assignment. Both versions indexed the exact same absolute paths.

| Measurement | Schema 2 | Schema 3 |
|---|---:|---:|
| Database bytes | 47,935,488 | 20,496,384 |
| Build peak RSS (KiB) | 62,600 | 24,792 |
| Build wall seconds | 1.397 | 0.933 |
| Literal query peak RSS (KiB) | 23,032 | 10,244 |
| Literal query wall seconds | 0.081 | 0.015 |
| Caller query peak RSS (KiB) | 18,180 | 21,520 |
| Caller query wall seconds | 0.088 | 0.062 |

The literal query was `-4 needle`; the caller query was `-3 leaf`. Their complete
outputs were byte-for-byte equal between versions. Peak RSS is measured for
each process using Linux `wait4`; it is not an application-level allocation
measurement. Timings include process startup/output and are affected by caching
and run order. There was no cache eviction or repetition, and differences in
parser traversal are included in build timings. The generator/runner's inherited
memory can also impose a floor on peak RSS measurements.

This run supports lower persistent storage and lower build memory for this
workload. Query memory did not improve uniformly: the caller query's peak RSS
increased. Do not extrapolate these timings or ratios to a kernel tree.

## Reproduce

Build a baseline executable from `af74e35` in a separate source directory and
the candidate executable from the current source. Then run:

```bash
python3 scripts/benchmark-storage.py \
  --before /path/to/baseline/target/release/rscope \
  --after /path/to/candidate/target/release/rscope
```

The script generates inputs and records each process's timing/memory, database
sizes, and output-equality checks. It retains its files and `summary.json` in
the printed temporary directory. Change `--files` or `--groups` to scale the
synthetic corpus. File-path lengths affect baseline database size.

Original run artifacts: `/tmp/rscope-storage-bench-mwmvt5q2/summary.json` and
the sibling input/output files. These temporary artifacts may be cleaned up.
The script captures the same workload and measurement method.

## Separate parser limit observed

A diagnostic with 1,000 consecutive comment lines in one Python file spent
about 0.34 seconds inside Tree-sitter parsing, while extraction took less than
0.001 seconds in that debug run. A 5,000-comment run exceeded an eight-second
diagnostic timeout. This is a different input shape and build mode from the
table above. The long-comment parser behavior remains unresolved; caching the
AST body-field lookup does not fix it. The large storage regression fixture
uses a multiline string to avoid conflating source-retention checks with this
parser stress case.

## Public snapshot reproduction boundary

Historical source revisions and temporary raw artifacts referenced above are
not included in this fresh-history snapshot. Recorded results are historical
observations; comparisons requiring those revisions cannot be reproduced from
this checkout alone. Current scripts can measure available binaries.
