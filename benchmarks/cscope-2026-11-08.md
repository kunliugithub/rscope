# Cscope 15.9 source-corpus experiment

This experiment tested rscope against `/path/to/cscope-15.9`.
The tree was used as read-only test input and to verify result locations; its
implementation was not copied into rscope. No source or Emacs configuration was
modified. Product code was unchanged from the partial-mode baseline d37125c.

## Selection and parser acceptance

All `.c` and `.h` files recursively under the supplied tree, excluding `.git`:

| Measurement | Observed |
|---|---:|
| Selected files | 42 (31 C, 11 headers) |
| Source lines | 50,719 |
| Source bytes | 2,311,127 |
| Files parsing cleanly | 32 |
| Files with parser errors | 10 |
| Read failures | 0 |
| Outermost error regions | 253 |

This selection includes `contrib/webcscope/hilite.c`, which has a separate main
function. The lexer/yacc inputs `scanner.l`, `fscanner.l`, and `egrep.y` are not
supported and were not selected. Their supplied generated C files were included.
Parser acceptance is not a measure of extraction correctness or completeness.

Files with errors: `dir.c` (5 regions), `egrep.c` (5), `exec.c` (1),
`fscanner.c` (125), `input.c` (1), `main.c` (1), `mouse.c` (5), `mypopen.c` (1),
`scanner.c` (82), and `snprintf.c` (27). The generated scanner/parser files
account for 212 of 253 regions; region counts do not reflect how much source
or how many definitions were lost.

## Builds and measurements

The strict build stopped on `src/dir.c:399`, where a statement-like
`HANDLE_OPTION_ARGUMENT(i, s)` macro invocation precedes `break`. The error
extends beyond the immediate macro location into later recovery. Strict exit
status was 1 after 0.025 seconds; no strict database was produced. This is not
a complete strict-build benchmark.

The full selection was then indexed with the existing experimental flag:

```bash
./target/release/rscope -b --allow-parse-errors \
  -f target/cscope-test/rscope.db -i target/cscope-test/rscope.files
```

| Partial-build measurement | Observed |
|---|---:|
| Elapsed time | 0.649 seconds |
| User CPU time | 0.598 seconds |
| System CPU time | 0.028 seconds |
| Peak RSS | 103,732 KiB (101.3 MiB) |
| Database bytes | 2,695,168 (2.57 MiB) |
| Indexed files | 42 |
| Stored occurrences | 24,360 |
| Affected files / saved diagnostics | 10 / 253 |
| SQLite integrity check | ok |

Single release run, after scanning sources; no cache eviction or repeated-run
statistics. Metrics use `perf_counter` and Linux `wait4` around the executable.
This is a partial index and these numbers are not a completeness claim.

The peak memory is higher than in the earlier HID experiment, despite fewer
files. The input includes a 1,800,055-byte, 32,093-line generated `fscanner.c`.
Per-file parser/AST/record memory remains relevant, but this run did not profile
which allocation caused the peak. File counts alone cannot predict memory use.

## Verified navigation examples

Definition lookup works for:

```bash
./target/release/rscope -dL -f target/cscope-test/rscope.db -1 findsymbol
```

It returns `src/find.c:89`. Caller lookup for `compath` returns seven call-site
lines in `src/dir.c`, with contexts such as addsrcdir, addincdir, incfile, and
addsrcfile. These examples establish specific useful results, not complete
coverage of their callers.

There is a clear missing definition:

```bash
./target/release/rscope -dL -f target/cscope-test/rscope.db -1 main
```

This returns only `contrib/webcscope/hilite.c:171`. That is a real separate
definition, but it omits the actual program entry point at `src/main.c:289`.
The parser has one ERROR region from `src/main.c:288` to `1092`, containing the
large main function. Skipping that region removes its definition from the index.
The precise triggering construct within that large region was not reduced here.

Live text search still finds the intended signature:

```bash
./target/release/rscope -dL -f target/cscope-test/rscope.db \
  -4 'main(int argc, char **argv)'
```

It returns `src/main.c:289`. Batch Emacs/xcscope verified both the missing
navigation target in definition results and successful text navigation to line
289. A nonempty definition result can therefore still omit the desired site.

## Try it in Emacs

Keep the current rscope executable and database name; select this test directory:

```elisp
(setq cscope-program "/path/to/rscope/target/release/rscope"
      cscope-database-file "rscope.db"
      cscope-initial-directory "/path/to/rscope/target/cscope-test/"
      cscope-database-regexps nil)
```

Open `/path/to/cscope-15.9/src/main.c` and use:

1. `M-.` with `main`: returns the web helper, omitting the core main function.
2. `M-,` with `main(int argc, char **argv)`: finds the core definition at line 289.
3. `M-.` with `findsymbol`: finds `src/find.c:89`.

Every query warns about the partial index. Set `cscope-initial-directory` back
to nil and restore prior database settings when returning to normal discovery.

## Artifacts

All generated inputs/results are under ignored `target/cscope-test/`:
`rscope.files`, `rscope.db`, strict/partial build metrics and logs,
`diagnosis/files.tsv`, `diagnosis/errors.tsv`, and `emacs-smoke.el`.
The original kernel test database and the root demo database remain separate.

This corpus has fewer files with errors than HID, but still exposes macro and
generated-code limitations. It does not demonstrate reliable complete Cscope
source navigation. No parser/extraction fixes or policy changes were made.
