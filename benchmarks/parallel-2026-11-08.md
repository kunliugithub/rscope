# Parallel indexing experiment — 2026-11-08

Implemented opt-in parallel source reading/parsing/extraction, a bounded result
channel, and one SQLite writer. The existing atomic replacement protocol and
grammar/extraction/index versions are preserved. No dependencies were added.

## Corpus and method

- Main corpus: complete `src/**/*.rs` trees from locked Cargo packages
  `regex 1.13.1`, `regex-automata 0.4.18`, and `regex-syntax 0.8.11`.
  117 files, 135,469 lines, 4,684,621 source bytes; strict parsing, no recovery.
- Supplemental corpora: the same fd v10.5.0 production Rust selection and
  google-java-format v1.37.0 core Java selection documented in
  [the earlier corpus experiment](rust-java-2026-11-08.md).
- A broader attempted corpus of all resolved dependencies’ Rust `src` trees
  (2,010 files / 1,136,015 lines) failed strict parsing in
  `anyhow-1.0.104/src/ensure.rs:134:28`. No timing from that failed attempt is
  presented as a successful build. The regex selection is a separate, explicitly
  scoped corpus, not a claim of complete dependency or Rust grammar coverage.
- Baseline: clean source from commit `ec6efdf0282f0c6a2ca2bfca384c54b524a23f88`,
  rebuilt using the same Rust 1.99.1 toolchain, lockfile, release profile, and
  native tools as the parallel implementation. The parallel builds enable
  `--profile`; the old binary has no profiler. Both use strict mode.
- Linux x86_64 VM, eight available vCPUs; host reports Intel i5-10400.
  No exclusive CPU reservation or CPU pinning. No tests/compilation were launched
  by this session during the final measured runs.
- Three builds per configuration, shuffled together using seed 20261108.
  Queue capacity equals requested workers. Each build replaces its variant’s
  previous database; initial runs create it. Five repetitions of each of nine
  queries per variant follow. Query order is fixed, not randomized.
- Warm/uncontrolled caches: inputs are hashed before runs and validation reads
  each database between builds. No cache eviction. All source content hashes
  matched afterward. Corpus sources were used as indexing inputs; fd/Java
  apps and build scripts were not executed. Cargo ran its normal dependency
  build scripts when building rscope. No corpus source files were modified.
- Wall time surrounds the helper subprocess and includes process startup,
  commit, synchronization, and atomic publication. The native helper uses
  `wait4` for child CPU and peak RSS (Linux KiB), avoiding inherited Python
  pre-exec memory in direct-fork measurements. Measurement helper compilation
  and database/query correctness checks are outside the timed build.

## Main results

| Configuration | Median build wall | Median peak RSS | Speedup vs old binary |
|---|---:|---:|---:|
| Previous serial binary | 1.104 s | 30,336 KiB | 1.00× |
| New serial path (`--jobs 1`) | 1.017 s | 30,496 KiB | 1.09× |
| 2 workers | 0.726 s | 36,652 KiB | 1.52× |
| 4 workers | 0.626 s | 48,164 KiB | 1.76× |
| 8 workers | 0.557 s | 62,808 KiB | 1.98× |

Four workers reduced median elapsed time by 43.3%; eight by 49.6%.
These are whole-build improvements, including serial index creation and
publication. They are specific to these selections and this machine; three
repetitions do not establish tight confidence intervals or kernel-scale behavior.

| Configuration | Three wall-time observations (seconds; execution order per configuration) |
|---|---|
| before | 1.104212, 0.993328, 1.118627 |
| jobs1 | 0.901619, 1.016710, 1.110190 |
| jobs2 | 0.725512, 0.743133, 0.659295 |
| jobs4 | 0.626073, 0.543405, 0.633093 |
| jobs8 | 0.556741, 0.477212, 0.581044 |

The normalized index contains 109,947 occurrence rows. Physical database
sizes range from 12,443,648 to 12,447,744 bytes as insertion order changes.
Different file IDs/page layouts are expected; byte-for-byte database equality
is not the correctness contract.

## Where the time goes

Profiler fields below are medians of each field independently, so columns
need not add to the median total. Worker read/parse measurements are sums of
wall times, not CPU times, and overlap the pipeline and writer.

| Workers | Pipeline wall | Read sum | Parse/extract sum | Insert time | Index creation | Commit/publication |
|---|---:|---:|---:|---:|---:|---:|
| jobs1 | 0.693 s | 0.004 s | 0.601 s | 0.077 s | 0.141 s | 0.185 s |
| jobs2 | 0.341 s | 0.008 s | 0.642 s | 0.081 s | 0.135 s | 0.242 s |
| jobs4 | 0.215 s | 0.008 s | 0.684 s | 0.092 s | 0.144 s | 0.252 s |
| jobs8 | 0.187 s | 0.023 s | 0.937 s | 0.110 s | 0.137 s | 0.226 s |

The serial profile confirms parsing/extraction is the largest phase.
Parallelism shortens the pipeline; index creation and durable publication
continue to limit whole-build speedup. Summed worker time increases under
concurrency, so eight workers should not be interpreted as eightfold efficiency.

These small builds are particularly sensitive to process and filesystem noise.
Java was fastest at two workers in this run. More workers are not uniformly
better, and memory rises with concurrency; serial remains the default.

## Correctness and editor integration

- Every one of 45 successful measured builds passed SQLite integrity checking.
  Sorted files (including freshness metadata), occurrences, parse diagnostics,
  and index metadata were streamed into SHA-256 digests and matched across
  all worker counts and the previous binary within each corpus.
- All nine query modes matched byte-for-byte for every configuration and
  repetition: 675 query executions. Patterns: `new` on regex, `scan` on fd,
  `formatSource` on Java; file regex `\.(rs|java|c|h|py)$`, import regex `.*`.
  Some write lookups can be empty; dedicated fixture tests exercise writes.
- On regex, previous/four-worker definition-query medians were
  6.55/6.47 ms; caller-query medians were
  10.58/10.23 ms.
  These include helper/process startup and result output, and support no
  sub-2ms or improved query-latency claim.
- Mixed-language regression tests compare all extracted records and all nine
  query modes at 2/4/8 workers with queue capacities 0/1, including duplicate
  paths. Separate tests cover partial-C diagnostics/warnings, invalid UTF-8,
  parse failure preserving the prior DB, build-only flags, and producer cleanup
  when the consuming writer fails. Integration failure cases have deadlines.
- All 46 CLI integration tests plus one unit test passed; fmt and warning-free
  all-target Clippy passed. Four installed-xcscope 1.6 ERT tests passed on
  serial indexes and again on four-worker release-built indexes, checking all
  nine modes per language and following results to source.
- Equivalence is to the existing syntax extractor, not an independent accuracy
  oracle. Existing macro omissions, overload ambiguity, and C recovery limits
  remain. Neither semantic completeness nor compiler correctness was measured.

## Reproduce

The historical old-versus-new comparison used a pre-parallel source revision
from the earlier development repository. That revision and the original raw
artifact directories are not included in this fresh-history snapshot. The JSON
preserves recorded measurements; this public checkout alone cannot reproduce
the historical old-binary baseline or verify the omitted raw artifacts.

To measure the current implementation at different worker counts, build it and
provide a complete manifest of readable source files (paths containing spaces
must use shell quoting):

```bash
cargo build --release --locked
python3 scripts/benchmark-parallel.py --binary target/release/rscope --manifest rscope.files --output target/parallel-reproduction --symbol new
```

This runs the current serial and 2/4/8-worker configurations, checking normalized
database records and queries. It measures your selected corpus and environment;
it does not reproduce the historical 43.3% old-versus-new result. An independently
available baseline executable can be supplied with `--baseline PATH`.

The output directory must be new. Requires Linux, Python 3, and a native C
compiler (`cc`). The helper is compiled from this repository’s
`scripts/measure-command.c`; no external benchmark dependency is installed.
Use the corresponding downloaded-source manifests and symbols for fd/Java.

Committed [measurement data](parallel-2026-11-08.json) contains individual
build observations/profiles, query medians, schedules, binary hashes, and
normalized database digests. Full stdout/stderr, per-query observations,
source hashes, and manifests are ignored artifacts under
`target/parallel-benchmark/{regex,fd,java}-final/`. The earlier
`regex-results/` directory is exploratory and is not used for final claims.
