# Rust and Java source-corpus validation — 2026-11-08

Pinned source releases from two established command-line tools:

- [fd v10.5.0](https://github.com/sharkdp/fd/tree/v10.5.0), a Rust file finder.
- [google-java-format v1.37.0](https://github.com/google/google-java-format/tree/v1.37.0), a Java formatter.

The archives were downloaded from GitHub's codeload service and extracted under
`target/external-test/`. Upstream source files were unchanged; SHA-256 hashes of
every selected file matched after validation. Archives, source, manifests,
databases, and raw measurements are ignored build artifacts, not vendored code.
No upstream build scripts or applications were executed.

Both strict builds succeeded, without parse recovery. SQLite `integrity_check`
returned `ok` for both databases. Java plugins, test classes, and formatting test
resources were excluded by selecting the core production source tree up front.
Rust's production source tree contains inline conditional test modules; these
were indexed because rscope does not evaluate build configuration.

These are single sequential release-binary runs on small, recently read source
sets, not cold-cache or scale benchmarks. Wall time used Python
`time.perf_counter()` around process creation/completion; CPU/RSS used the
individual child process's `os.wait4()` resource usage on Linux. fd used
0.049164 s user / 0 s system CPU; Java used 0.167030 s user / 0.004073 s system.
The release binary uses Tree-sitter 0.25.10, Rust grammar 0.24.2, Java grammar
0.23.5, and the existing lean schema 3 storage.

## Navigation checks

Twenty CLI checks passed: all nine query modes for each corpus, with an extra
definition check for each. Every returned source snippet was compared with its
file and line (file-name results use the existing synthetic line-1 format).
Representative expected source locations were checked independently:

| Query | fd target | Java target (under `core/src/main/java/com/google/googlejavaformat/java/`) |
|---|---|---|
| Definition | `main` → `src/main.rs:62`; `scan` → `src/walk.rs:685` | `main` → `Main.java:68`; `formatSource` → `Formatter.java:165` |
| Callees | `main` includes `run` at `src/main.rs:63` | `main` includes `main` at `Main.java:69` |
| Callers | `scan` includes `run` at `src/main.rs:111` | `formatSource` includes `call` at `FormatFileCallable.java:75` |
| Occurrences | `pattern_has_uppercase_char` at `src/regex_helper.rs:5` | `formatSource` at `Formatter.java:165` |
| Literal / regex text | `fn main()` / `^fn main\(\)` at `src/main.rs:62` | `public static void main` at `Main.java:68` |
| File regex | `/src/main\.rs$` | `/java/Main\.java$` |
| Written import regex | `^std::sync::Arc$` includes `src/main.rs:20` | `^java\.lang\.Math\.min$` includes `Main.java:17` |
| Writes | `should_warn` includes `src/main.rs:199` | `options` includes `Formatter.java:89` |

Installed xcscope 1.6 in batch Emacs also found and followed four real-corpus
results: Rust `scan` definition and caller, Java `formatSource` definition and
caller, at the exact lines above. No changes to xcscope or permanent Emacs
configuration were needed. Separately, the committed fixture smoke suite checks
all nine modes through xcscope for Python, C, Rust, and Java.

This establishes useful navigation on these selections, not complete semantic
accuracy. Two visible boundaries:

- fd's `pattern_has_uppercase_char` caller search returns the ordinary closure
  call at `src/main.rs:255`. Calls inside `assert!(...)`, such as
  `src/regex_helper.rs:83`, are omitted because Rust macro arguments are opaque.
  Text search still finds those lines.
- Java's three `formatSource` overload definitions are combined. Calls from one
  overload to another have the same bare caller/callee name. Likewise `main`
  calls another `main` overload; that result does not prove self-recursion.

No compiler, overload/type resolution, or exhaustive definition/call oracle was
used. Java/Rust application execution was outside this navigation check.

## Try the existing databases

From the rscope repository root:

```bash
./target/release/rscope -dL -f target/external-test/fd-10.5.0/cscope.out -1 scan
./target/release/rscope -dL -f target/external-test/fd-10.5.0/cscope.out -3 scan
./target/release/rscope -dL -f target/external-test/google-java-format-1.37.0/cscope.out -1 formatSource
./target/release/rscope -dL -f target/external-test/google-java-format-1.37.0/cscope.out -3 formatSource
```

For Emacs, open a source file in either downloaded project and set the database
root for that project, for example:

```elisp
(setq cscope-program "/path/to/rscope/target/release/rscope"
      cscope-database-file "cscope.out"
      cscope-option-do-not-update-database t
      cscope-initial-directory
      "/path/to/rscope/target/external-test/fd-10.5.0/")
```

For Java, change `cscope-initial-directory` to
`/path/to/rscope/target/external-test/google-java-format-1.37.0/`.
Use the existing definition/caller commands and keybindings. Choose the relevant
project root when switching between these databases.

## Reproduce the selections

Download and extract these pinned archives under `target/external-test/`:

- `https://codeload.github.com/sharkdp/fd/tar.gz/refs/tags/v10.5.0`
- `https://codeload.github.com/google/google-java-format/tar.gz/refs/tags/v1.37.0`

From each extracted project root respectively:

```bash
# fd
rg --files src -g '*.rs' | sort > rscope.files
/path/to/rscope/target/release/rscope -b

# google-java-format
rg --files core/src/main/java -g '*.java' | sort > rscope.files
/path/to/rscope/target/release/rscope -b
```

Each build replaces that project's `cscope.out`. Raw build metrics, selected-file
hashes, and query results are in `target/external-test/build-results.json`,
`*-source-hashes.json`, and `query-checks.json`; the local rerunnable query check
is `target/external-test/check-queries.py`. These generated files disappear if
`target/` is cleaned.
